- Every Discord server function must call requireOwner() first (owner-only password session cookie); server functions are public endpoints otherwise.
- Server-only helpers (session, Discord gateway, AI calls) live in `src/lib/*.server.ts`; `*.functions.ts` and route files must not export them or import-protection breaks the client bundle.
- Streaming features (AI incident advisor) use a server route under `src/routes/api/` that checks `isOwner()` and dynamically imports `.server` modules inside the handler; server functions cannot stream NDJSON.
- Server analytics use a dedicated owner-protected server function and pure aggregation helpers; keep missing metrics null and label bounded audit samples so they cannot be mistaken for complete historical totals.
- Slash-command interactions live at `/api/public/discord-interactions`, verified by Discord's Ed25519 signature (public key auto-fetched from `oauth2/applications/@me`) instead of `requireOwner` — the caller is Discord, not a browser session. Commands are registered globally via `applications/{id}/commands`: guild-scoped command routes (`guilds/{id}/commands`) are rejected by the Discord gateway proxy, so never use them. Registration must merge with (never wipe) existing commands, since other tools may have registered their own.
- Register and modify commands individually via POST/PATCH, never bulk PUT, to preserve unrelated definitions and IDs; custom responses are stored in a server-only Cloud table, accessed only after the owner-cookie check or verified Discord signature.
- Native Discord server applications are not available to bots through the documented API; do not substitute pending guild members or use user tokens to simulate this workflow.
- The 24/7 bot is a standalone Node process in `bot/` hosted by the owner (Lovable cannot keep a Gateway connection alive); it pulls settings from `/api/public/bot-sync` with the BOT_SYNC_SECRET bearer, which also proxies AI replies so the AI key stays server-side.
- Prefix commands are guild-specific entries in bot settings, edited through dedicated owner-protected functions; general settings saves preserve them, and the Node bot uses a pure tested resolver before AI/keyword replies to enforce command permissions.
- Built-in voice commands run before custom replies and use independent guild voiceAccess role allowlists (null means legacy current-channel ManageChannels; empty means owner/admin only); recheck fresh member roles on each command and author-bound component interaction, including pv access for panel lock/unlock, to prevent bypasses. Persist Connect-only restoration snapshots on the VPS.
- Voice access is edited only through owner-protected admin functions in existing bot settings; unrelated settings/command saves preserve voiceAccess so stale forms cannot undo access changes. The Oracle process must run compatible code to enforce synchronized settings.
- Dashboard and configuration presentation share global semantic theme tokens and CSS motion primitives; respect reduced-motion preferences and keep Discord logic separate from visual changes.
- Bot monitoring uses authenticated periodic reports persisted as one bounded snapshot; accept only fixed event codes, never raw logs or message contents, to prevent credential leaks. Report age, not Discord REST availability, determines live presence.
- The /status interaction reads only connection state and process uptime from the authenticated bot snapshot after Discord signature verification; never use the website process uptime or expose monitoring events to Discord members.
- Installation downloads contain only public configuration and empty credential fields; connection functions return secret presence only, never stored secret values.
- The live status page renders client-side after its owner-protected loader, preventing heartbeat changes between SSR and hydration from producing mismatched live data.
- The public/downloads/bot-oracle.zip archive is a public source-only distribution; regenerate and inspect it whenever bot sources change, using an explicit allowlist, never including .env, data, repository metadata or dependencies. Updates preserve the VPS's existing configuration.

## FWU product and development rules

- The official product name is **FWU V2** (owner decision 2026-11-26). The name appears only on the dashboard and in documentation, never in Discord: no "FWU" in embeds, messages, audit-log reasons, created channel/role names or command descriptions. Dedicated bots sign with their own name, the main bot is "Bot principal" and signs nothing. `bot/discord-branding.test.js` enforces this. Keep the existing Her? V5 implementation and validated features; migrate identity and presentation incrementally rather than rebuilding the project.
- Discord First: Discord is the primary administration surface. The dashboard may configure and observe the bot, but everyday administration must not require it. Keep the current bot sync/API dependency server-side while designing a safe transition; never expose AI keys or sync credentials to Discord clients.
- Maintain strict per-guild configuration and data isolation for the FWU main server and MZ secondary server. MZ stays disabled until its configuration is explicitly validated. Central logs must retain the source guild identity and must never cross-post private data between source servers.
- Provide an interactive `/setup` flow using Discord buttons, selects and modals. Recheck permissions and guild context on every interaction; bind privileged component actions to their author where applicable.
- Preserve the existing SYS+ and ADMIN+ tiers and add WHITELIST as an internal limit exemption only. WHITELIST must never bypass Discord-native permissions, role hierarchy, ownership checks, or authorization for privileged actions.
- DOG marker roles are per owner (owner decision 2026-11-24): `En laisse (<owner display name>)`, one role shared by all leashes of that owner, deleted once nobody holds it; the former shared `En laisse` role is still recognised and migrated. Do not append a product name. Preserve persistent leash state and safe restoration behavior.
- Tier 0 (explicit tier-0 mapping via `/quota palier` or the configured owner) is untouchable: server mute/deafen, timeout and bans are reverted instantly by SUCK ME (`bot/tier0-shield.js`); nickname/role changes are reverted unless made by the member, the owner or the bot. Never infer any tier, power or protection from a role name (decision 2026-11-25: a SYS+ could create a personal role "Me 0 %"); `%` is refused in personal/custom role names.
- Granting roles (decision 2026-11-25): every bot path that gives a role goes through `bot/role-grant-guard.js`. Protected roles are the SYS+, ADMIN+ and WHITELIST roles, roles explicitly mapped to tier 0/1/5/10/50, and roles carrying privileged permissions (Administrator, Ban, Kick, Timeout, Manage roles/channels/messages/nicknames/webhooks, Move/Mute/Deafen, Mention everyone, View audit log…). Manual commands may give them only when the actor is the configured owner; automatic grants (shop, levels, birthday, reaction/CAPTCHA/screening, auto-roles, automation rules, quarantine, rankall) never give them. Restorations of roles a member already had (quarantine end, DOG, tier-0 shield) are not grants. Prefix commands run under `runAsActor` like slash commands.
- LOCKNAME must restore the protected nickname automatically and isolate its state by guild/member. Do not overwrite a member's state from another guild.
- WAOUF is SYS+-only and may be used only in text channels explicitly allowed by that guild's configuration.
- `/pnd-add` is restricted to the configured Discord owner ID only. Do not treat guild ownership, Administrator, SYS+, or ADMIN+ as equivalent. Keep the owner ID in trusted server-side configuration and never print secrets.
- Keep MZ Stream Center and streaming integrations isolated to MZ configuration. Do not activate MZ or connect production services while developing or testing.
- No faction system. Preserve approved community, economy, administration, AI, music and automation capabilities; do not remove existing features as a shortcut.
- For ordinary workspace changes, bug fixes, tests, refactors, documentation, and compatible dependencies, proceed autonomously in coherent reviewable batches. Ask for human approval only for production deployment, Oracle/VPS access, secrets/tokens, destructive production data operations, activating a Discord server, changing sensitive production permissions, purchases, or a product decision that changes the accepted specification.
- Never use the production bot token for tests. Prefer local mocks and a separate staging bot/application and guild. Redact secrets and sensitive member data from test output and reports.
- Keep a reversible checkpoint before substantial batches. Do not rewrite published Lovable history, force-push, or copy V3/V4 Git metadata as the V5 history. If the workspace Git metadata is unavailable, recover the matching V5 source history or establish a clearly documented local baseline without claiming it is prior history.
- Do not mark a feature complete until relevant automated tests pass and any Discord-dependent behavior has a staging validation plan. Report exact commands and distinguish executed tests from manual checks.
